# Single-file Docker deployment

[简体中文](README_CN.md)

Save `compose.yaml` in an empty directory and run:

```bash
docker compose up -d
```

Open `http://localhost:3100`. The initial account is `root` and the initial password is
`change-me-root-password`; change it after signing in. This recipe requires an API
image containing `/usr/local/bin/1flowbase-initialize` and
`/usr/local/bin/1flowbase-api-start`. Images published before this recipe do not contain them.

The initialization service runs a POSIX shell script built into the API image without
using Node.js. It creates mounted
directories and `config/.env`, generates a separate database password and encryption
master key, then exits. PostgreSQL and the API read the saved configuration.
Recreating containers preserves it. Keep the configuration together with the database
and uploaded files; an existing database without its configuration fails to start.

Before first startup, an optional Compose `.env` next to `compose.yaml` can set
`WEB_PORT`, `FLOWBASE_API_SERVER_VERSION`, `FLOWBASE_WEB_VERSION`,
`BOOTSTRAP_ROOT_ACCOUNT`, `BOOTSTRAP_ROOT_PASSWORD`, `POSTGRES_PASSWORD`, and
`API_PROVIDER_SECRET_MASTER_KEY`. Initialization values apply only when creating
`config/.env`; changing them does not reset existing accounts or rotate existing secrets.
The default is HTTP. Set `API_COOKIE_SECURE=true` for a browser-facing HTTPS entry,
including TLS terminated by an outer nginx proxy. Set `API_ALLOWED_ORIGINS` when
browser clients access the API from a different origin.

`config/.env` contains secrets. Do not commit it or delete it to reset an account.
This recipe is for a fresh deployment with bundled PostgreSQL. Existing deployments,
external PostgreSQL, and portable recovery retain the deployment scripts and recipes
documented in [the Docker guide](../README.md).

## Nginx configuration and upgrades

At startup, the Web image exports its configuration through the directory mount
`./web/nginx:/config/nginx`. No configuration file needs to exist beforehand:

- `web/nginx/nginx.default.conf` is the current image's reference configuration. It is refreshed on every startup and includes WebSocket forwarding for `/api/` and `/v1/`. Do not edit this file.
- `web/nginx/nginx.conf` is an optional complete override. It is not created automatically. When present, it takes precedence and is preserved across restarts, recreation and upgrades. Compare it with the reference configuration after upgrading.

Without an override, upgrading the image automatically applies updated defaults.
To customize the configuration, run these commands in the deployment directory:

```bash
sudo cp web/nginx/nginx.default.conf web/nginx/nginx.conf
# Edit web/nginx/nginx.conf with sudo, then validate and recreate Web.
docker compose run --rm --no-deps web nginx -t &&
docker compose up -d --no-deps --force-recreate web
```

Startup validates the Nginx configuration. Errors appear in `docker compose logs web`
and prevent startup. Move the custom `web/nginx/nginx.conf` aside and recreate Web
to restore current image defaults; do not delete the entire configuration directory.

### Migrating an existing deployment

This mechanism requires a Web image containing `40-flowbase-nginx.sh`; updating only
Compose while keeping an older image will not export a template. Update the Compose
file along with the Web image. Replace an existing
`./web/nginx.conf:/etc/nginx/conf.d/default.conf:ro` mount with
`./web/nginx:/config/nginx`, keeping external-npm and other mounts.
If you need to retain custom rules, first verify that the old path is a regular file,
then copy it to `web/nginx/nginx.conf`. Otherwise, use image defaults. If Docker
previously created a directory at the old file path, move it aside as a backup;
do not copy that directory as a configuration file.

New images still honor legacy direct file mounts and log a migration notice, but
these mounts override updated image defaults. The SSH WebSocket fix is not inserted
into custom configurations automatically: add
`proxy_set_header Upgrade $http_upgrade;` and
`proxy_set_header Connection $connection_upgrade;` inside `/api/`, or remove the
override to use the new defaults.

### A public static site with FRP

If a public server hosts the frontend build separately and forwards API requests
through FRP to Docker port `3100`, the public Nginx server also needs SPA fallback:

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

Place this rule inside the public domain's `server` block, with `root` pointing to
the build directory containing `index.html`. Update an existing `location /` rather
than adding a duplicate. `/settings/...` and `/mcp/authorize` are frontend routes,
not physical files or backend API endpoints. Docker's fallback cannot fix a 404
returned by the public static server.
The public API proxy must preserve request paths, Host, the external HTTPS scheme
and WebSocket upgrade headers. Forward the `/.well-known/oauth-*` discovery paths
used by MCP instead of serving them only from the public certificate-validation
directory. Keep the public frontend build and Docker Web image versions aligned.

## Automatic domestic registry mirroring

`aliyun image sync` is a separate GitHub Actions workflow. It runs after a successful
`container images` workflow on the `latest` branch. A mirror failure does not change
the GHCR or GitHub Release result. The new mirror workflow and its script must be
present on the repository's default branch for `workflow_run` to trigger automatically.

Configure Settings → Secrets and variables → Actions:

| Name | Type | Value |
| --- | --- | --- |
| `ACR_SYNC_ENABLED` | Variable | `true` to enable; any other value disables syncing |
| `ACR_REGISTRY` | Variable | Public registry hostname, without `https://` |
| `ACR_API_REPOSITORY` | Variable | API `namespace/repository` |
| `ACR_WEB_REPOSITORY` | Variable | Web `namespace/repository` |
| `ACR_POSTGRES_REPOSITORY` | Variable | PostgreSQL `namespace/repository` |
| `POSTGRES_SOURCE_IMAGE` | Variable | `docker.io/library/postgres:18-alpine`, or a pinned PostgreSQL 18 minor release |
| `ACR_USERNAME` | Variable | Registry login username |
| `ACR_PASSWORD` | Secret | Registry login password |

The mirror processes only components successfully published by the source run. Each
component uses its own version, and its image revision must match the publishing
commit. API and Web use separate repositories, each publishing `v<version>` and `latest`.
PostgreSQL mirrors the official 18 Alpine image into its own repository with
`18.<minor>-alpine` and `18-alpine` tags. Its deployment never uses a cross-major `latest` tag. Copying preserves runtime images
and per-platform image digests for `linux/amd64` and `linux/arm64` without rebuilding.
Personal ACR does not support OCI build attestations, so they are excluded from the
destination index. Its top-level digest changes; verification compares both runtime
image digests individually. The copier is regctl v0.11.6, pinned by version and checksum,
used only in CI without adding application dependencies.
A component's domestic latest tag is updated
only when GHCR latest still points to that image.

Retry a failed mirror run, or select Run workflow and provide the successful source
`container images` run ID from this repository's `latest` branch. Syncing fails if a
candidate was not promoted to an official version, the source image was overwritten
by another commit, or runtime image digests cannot be preserved. Verification evidence is saved
in the mirror run's `aliyun-image-sync-*` artifact.

## Deploy from domestic mirrors

Save `compose.aliyun.yaml` as `compose.yaml` in an empty directory and run `docker compose up -d`.
API and Web pull `latest` from separate Aliyun repositories; PostgreSQL uses
`taichuy/postgres:18-alpine`. API and init use the same API image. Startup checks for
remote updates while preserving existing configuration and database files.

An optional `.env` can override `FLOWBASE_REGISTRY`, `FLOWBASE_API_REPOSITORY`,
`FLOWBASE_WEB_REPOSITORY`, `FLOWBASE_POSTGRES_REPOSITORY`, and each component's version:
`FLOWBASE_API_SERVER_VERSION`, `FLOWBASE_WEB_VERSION`, `FLOWBASE_POSTGRES_VERSION`.
To pin this tested release, use `v0.5.6`, `v0.5.6`, and `18.6-alpine` respectively.
Port and bootstrap account options remain the same as above.

The [English Wiki guide](https://github.com/taichuy/1flowbase/wiki/Docker-Aliyun-Deployment)
includes the complete single-file configuration, upgrade and persistence instructions.
For a private registry, log in on the deployment machine before starting services.
