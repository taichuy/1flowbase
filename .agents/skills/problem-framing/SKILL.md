# Problem Framing

## Goal

在最小上下文预算内塑造清晰目标地形：先理解问题，再拆需求，最后给方案。只保留会改变目标、边界、取舍或验收的内容。

本 Skill 只负责对齐与决策，不修改产品代码、测试、migration、schema 或运行时行为。

## Core Principles

- **以始为终**：围绕最终可观察结果组织信息；不能帮助决策、行动或验证的 token 删除。
- **先推理后结论**：先分析事实、机制和约束，避免用预设结论反向辩护。
- **第一性原理**：追到足以解释结果的底层条件，不堆术语或抽象层级。
- **奥卡姆剃刀**：优先选择满足目标的最小机制，不为完整感增加流程和产物。
- **隐藏因果**：指出会实质改变方案的隐含问题，并用“条件 → 机制 → 结果”解释。
- **通俗易懂**：使用用户语言和具体结果；术语只在能提高精度时出现。
- **隐式优先**：给模型目标、约束和催化关键词，不用细碎步骤限制原生寻优能力。
- **升温后收敛**：三个方向用于短暂发散采样；最终建议负责降温收敛。

不要向用户展示内部思维链。复杂推理只输出简短的关键依据、因果链和可验证结论。

## Entry Gate

需求类请求先使用本 Skill；只有以下情况可直接进入实现：

- 纯查询或机械精确改动。
- 用户明确说“直接实现”“无需确认”或“跳过规划”。
- 已有用户确认的 issue / handoff，且当前工作未扩大边界。

未确认方案前停止在需求对齐；确认后再决定是否需要 issue。默认用一个 Standalone Complete Issue，只有用户要求、已有 parent issue，或确有多个独立决策 / workstream 时才升级 issue 树。

## Context Budget

- 只读当前请求、适用 AGENTS、直接相关文档和代码；默认只追一层影响面。
- 普通对齐目标为 300-600 中文字；复杂或高风险对齐目标为 600-1000 中文字。
- 每个方向通常 2-4 条短句；ASCII 图通常不超过 12 行。
- 最多 3 轮集中追问；能从仓库确认的事实不问用户。
- 证据不足时标记 `假设`，不要用冗长内容填满空白。
- 复杂度来自问题本身时允许展开，但每段都必须改变决策或验收。

## Analysis Order

严格按以下顺序思考和输出，不提前锚定推荐：

1. **现状**：分离事实、假设、未知点、不变量和触发本次讨论的矛盾。
2. **需求分析**：明确最终效果、范围、关键约束；用第一性原理、奥卡姆剃刀和隐藏因果解释真正问题。
3. **三个方向**：完整列出保守、平衡、激进，再做推荐。
4. **最终建议**：给唯一建议、关键理由和需要用户批准的点。

若信息不足以形成三个真实可执行方向，直接说明缺口并集中追问，不凑数。

## Alignment Format

默认使用以下骨架，不额外添加重复的“风险收益”“复杂度归属”等独立大节；相关内容写进各方向。

```markdown
## 现状
+- 已确认事实、关键未知与当前矛盾。
+
+## 需求分析
+- 最终目标与非目标。
+- 关键因果：条件 → 机制 → 结果。
+- 必须守住的约束或验收结果。
+
+## 三个方向
+### 保守
+- 方案内容：最小改动或维持现有边界。
+- 方案收益：即时收益、代价与主要风险。
+
+### 平衡
+- 方案内容：收敛核心问题，不过度扩张。
+- 方案收益：收益、代价与主要风险。
+
+### 激进
+- 方案内容：更彻底的重构、统一或前瞻设计。
+- 方案收益：长期收益、投入与主要风险。
+
+## 最终建议
+- 唯一推荐、关键依据、为何暂不选另外两个方向。
+- 需要用户确认：明确拍板点。
+```
+
+每个方向必须独立可执行；“方案收益”同时包含代价、隐藏成本和失败风险，避免再复制一份风险表。
+
+## UI And Logic Sketch
+
+涉及产品 UI、UX、页面流程、状态跳转或复杂逻辑时，在 `需求分析` 或对应方向下补一个短 ASCII 图。图只表达关键结构与主路径，不做高保真设计。
+
+```text
++---------------- Workspace ----------------+
+| [入口] -> [主操作] -> [结果/反馈]          |
+|                \-> [失败/空状态]           |
++-------------------------------------------+
+```
+
+## Decision Heuristics
+
+- **保守**：适合目标窄、风险高、证据不足或需要快速止损；不得用临时特判掩盖根因。
+- **平衡**：默认优先；把必要复杂度收敛到最理解业务、最靠近变化源的模块。
+- **激进**：只在现有边界持续制造系统性成本，且用户愿意承担迁移与验证投入时选择。
+- 软件设计不是消灭复杂度，而是把复杂度放到正确位置；不要扩散给多个调用方或隐式约定。
+- 后端是唯一数据来源；前端不承担输出兼容。接口字段保持后端 DTO / 领域语义原名。
+- 不用堆叠 if、静默 fallback、无语义 helper、flag 或 pass-through 层代替设计。
+- 用户方向与证据或硬约束冲突时，明确指出冲突、后果与更小 redesign，不盲从。
+
+方案可能新增公共抽象、接口、flag、通用 helper、重复校验或 pass-through 时，读取 `../_shared/design-rules.md`。
+
+## High-Risk Framing
+
+涉及 API / DTO / schema / migration / defaults / 历史数据 / 权限 / 状态归属 / 用户内容 / 跨前后端 contract 时，在短格式内额外明确：
+
+- 谁触发、成功与失败分别产生什么可观察结果。
+- 哪个模块承担复杂度，哪些边界不可破坏。
+- 数据、状态、权限或兼容的主要失败模式。
+- 用什么接口响应、测试、日志、截图或状态变化验收。
+
+若数学关系、算法、数据结构、状态机、图、队列、约束或概率能显著简化规则，可作为方案假设；否则不为炫技展开。
+
+## Questions
+
+只有缺失信息会改变方案、contract、数据、权限、用户内容或验收时才追问。一次集中给出当前全部阻塞问题，每题包含：
+
+- 可选项。
+- 推荐默认值。
+- 不同选择会改变什么。
+
+三轮后仍未知的内容写为假设或待确认项，不继续挤牙膏式追问。
+
+## After Approval
+
+用户确认方向后：
+
+1. 若只要求直接实现，切换到对应实现 Skill，并严格遵守已确认边界。
+2. 若需要开发计划，读取 `references/issue-lifecycle.md` 与 `references/artifacts.md`，默认生成一个 Standalone Complete Issue。
+3. 只有多决策或多 workstream 无法被单体 issue 安全承载时，才申请 L0/L1/L2/L3 issue 树。
+4. 涉及 defaults、contract、schema、state、permissions、migration、history 或 user content 时，按需读取 `references/domain-matrix.md`。
+5. 需要正式反方评审时读取 `references/options-and-red-team.md`；不要在普通对齐中默认增加 red-team 篇幅。
+6. issue 或 handoff 确认后，再使用 `frontend-development`、`backend-development`、`test-driven-development`；交付阶段使用 `qa-evaluation`。
+
+## Stop Conditions
+
+命中任一条件立即停止并等待用户：
+
+- 三个方向与唯一建议已可供拍板。
+- 当前阻塞问题已集中提出。
+- 证据不足以安全区分方向。
+- 用户修改或否定核心假设。
+- issue、ADR 或 implementation handoff 已可供审阅。
+
+不要在同一轮越过“方向确认 → issue 确认 → 实现”多个闸门，除非用户明确要求直接推进。
