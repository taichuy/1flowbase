# Problem Framing

## Outcome

把请求收敛为可决策、可检索、可验收的目标与计划。强制三方向用于发散后收敛，固定回复格式用于用户核对与后续计划复用；不以精简为由省略。

本 skill 只形成决策，不修改产品代码、测试、migration、schema 或运行时行为。

## Trigger and Evidence

- 功能差异、缺失能力、不可编辑或入口归属诊断会影响产品决策，应先对齐；纯事实查询、机械精确修改或用户明确直接实现可跳过。
- 复用当前任务已有目标、授权、AC 和证据；只补会改变可行方向或建议的未知。不能用实现探索替代用户目标，也不默认加载开发 / QA 的完整规则。
- 当前行为查源码与运行态；设计约束查 [DESIGN.md](../../../DESIGN.md)，后端先看 [api/AGENTS.md](../../../api/AGENTS.md) 和 [调用架构总览](../../../docs/architecture/interface-lifecycle.md)，详细 owner 查局部 AGENTS。按任务选取，不先读全项目架构。
- 文档表达约束，源码表达实际；发现冲突须说明差异与影响，不自动把现状当成获准目标。用户目标、权限、数据和已确认 contract 限定方案边界。

## Decision Readiness

- 仍需讨论时，在现状 / 需求分析前段明确列出待决问题、影响与建议默认值；能从当前源码查明的事实先查，不把检索任务交给用户。
- 三个方向是围绕这些问题的具体方案与决策试探：写清做什么、行为如何变化、接受什么代价。不能只给“少量 / 更完善 / 通用化”等抽象等级，也不能用不满足用户明确目标的方案凑数。
- 最终建议交付一个用户点头后即可执行的方案：对象与范围、关键行为和默认值、实施动作、可观察验收。只呈现决策需要的技术细节，不用内部 skill 调度、阅读路径或测试场景表代替方案。
- 验收自问：用户只回复“按建议做”，是否还缺必须重新询问的产品决策？若缺，先把该问题前置并给出有依据的推荐选项，再收敛方案；不能用“确认字段 / 入口后再制定计划”结尾。
- 关键事实确实不可取得且无法安全给默认值时，明确说明当前阻断问题与补齐方式，不能假装方案已可执行。非阻断未知作为显式假设，不追加开放式追问。

## Decision Logic

```text
证据 → 当前行为 → 与用户目标的差距 → 可观察验收
D = {保守, 平衡, 激进}
F = {d ∈ D | d 满足当前硬约束}
推荐 ∈ F
计划写集 ⊆ 已授权写集
```

三个方向解决同一目标，在范围、复杂度归属或风险偏好上有真实差异；不可行方向仍描述并给排除证据。`F` 为空时说明冲突与待决事项，不捏造可执行建议。最小方案以足够解决问题为前提，不按代码或文字最少选取。

- 第一性原理：拆出目标、事实、约束和失败模式；奥卡姆剃刀：删掉不能改变决策的假设与机制。
- 新证据的预期决策收益高于获取成本时才继续检索；收益无法量化时作有依据的定性判断，不伪造评分。关键未知无法查明时集中询问，其他缺口注明有界假设。
- 已有证据足以比较三个方向并给建议时停止取证。先输出可核验摘要，不展示内部思维链；催化词不能替代证据。

## Architecture Decisions

```text
Owner(m, x) ⇒ Authorized(m, x) ∧ Observable(m, x) ∧ Controllable(m, x)
```

`m` 是负责模块，`x` 是状态或职责；授权、可观察、可控制是必要条件，不足以单独推出所有权。再核对真值归属和处理所需状态 / 动作的能力，比较复杂度泄漏、协调与失败风险，不做无量纲依据的加权求和。

- 必要复杂度由最接近真值与变化源的 owner 吸收；公共接口简明，内部承接状态与协议细节。
- 有可验证的成熟算法、状态机、数据结构或约束时优先复用；新抽象的具体检查见 `../_shared/design-rules.md`，不因一个名称或 bool 就重开产品决策。
- 后端拥有业务 contract 与状态真值；前端消费原名 DTO，不以输出兼容或展示别名建立第二份业务真值。

## Response Contract

只要使用本 Skill，最终对齐答复必须完整使用以下 Markdown 骨架；不得省略、改名、合并、重排标题，也不得在 `现状` 前先写结论。该约束只作用于最终对齐答复，不要求工具过程更新套用模板。

```markdown
## 现状
已确认事实与证据；仍需讨论的问题在此明确列出，并说明影响。

## 需求分析
理想结果、成功标准、约束与待决选择；给出建议默认值及依据。

## 三个方向（升温发散）
### 保守
- 方案内容：...
- 综合收益：收益、代价与主要失败模式。

### 平衡
- 方案内容：...
- 综合收益：收益、代价与主要失败模式。

### 激进
- 方案内容：...
- 综合收益：收益、代价与主要失败模式。

## 最终建议（降温收敛）
唯一推荐与理由；明确对象、范围、行为 / 默认值、实施动作及验收，让用户确认后即可执行。确有阻断时回指前文具体问题，不以泛泛追问代替方案。
```

- 三个方向解决同一目标，在范围、复杂度归属或风险偏好上有真实差异；硬约束排除某方向时仍保留标题并写明排除证据，不编造可行性。
- 普通需求压缩每段内容，不省略标题或方向；复杂问题才展开。UI、UX、状态或复杂关系用短 ASCII 图表达主路径。

## Decision Gate

- 用户未确认方向时停止，不进入实现；用户明确要求直接实现时可跳过 issue 确认，但必须把结果、成功标准、权限、验证与停止条件交给 implementation Skill。
- 方向确认后只选择 Single Issue 或两层 Issue Tree；读取 `references/issue-lifecycle.md`。长计划还需满足 `references/long-running-work.md` 的 Delivery readiness。
- 新问题改变目标、source of truth、contract、数据影响、权限、用户内容或成功标准时，回到本 Skill；既定边界内的局部实现选择不重复请求批准。
