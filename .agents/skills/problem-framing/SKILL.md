# 从现状推到选择

这是决策对话。先让用户看见判断依据，再给建议；方向未确认时停在选择，不改产品。

1. **项目现状**：沿用户描述的动作找到负责它的页面、接口或状态，给能定位的事实。已有材料足以区分方案，就不再探索。
2. **用户需求**：谁在什么场景下，希望看到什么结果？把用户想改变的行为和仍需保留的行为分开。
3. **因果关系**：解释「当前机制 → 为什么出现这个差距 → 改哪个环节会改变结果」。区分观察和推测；只有会翻转建议的假设才值得再查。涉及排序、调度、权限或状态时，优先用成熟算法、状态转移或不变量说清关系，而不是枚举猜想。
4. **三个方案，比较结果**：保守、平衡、激进解决同一个需求。分别说明用户最终得到什么、代价由谁承担；方向不成立就说明哪个约束排除了它。差别应在结果或取舍，不是把同一实现拆成三步。
5. **一个建议**：结合**环境**（已有能力与限制）、**原则**（冲突时优先保什么）、**任务**（本次做到哪个可观察结果）选一个。只留下会改变选择的待确认项。

**例：**分页列表只能按当前页排序。用户要的是“全库最近更新”。先分页再排序会漏掉其他页的较新记录，调整表头解决不了这个差距。三个结果：仅本页有序；服务端先排序再分页，全库有序；建设可配置查询，让多个列表自定义排序。本次只有一张表需要全库有序，且已有分页接口，建议第二种：沿用查询 owner，用跨页样本看首屏是否出现最新记录。

## 从选择进入执行

一个连贯结果用 Single Issue，即使横跨前后端。需要跨上下文执行且有多个可独立集成结果的长计划用 Root → Delivery 两层 Issue Tree，执行前读[长计划约定](references/long-running-work.md)。用户已明确要求直接动手时，不为输出方案或建单重新索取同一授权。

需要落计划时查 [Issue 生命周期](references/issue-lifecycle.md) 或[交付物形态](references/artifacts.md)；遇到历史数据、权限或契约取舍查[领域边界](references/domain-matrix.md)，关键假设可能推翻建议时查[方案比较](references/options-and-red-team.md)。更多[示例](references/examples.md)仅用于校准表达尺度。
