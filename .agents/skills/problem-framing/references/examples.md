# Examples

示例只说明输出尺度，不是固定答案或字段清单。优先根据真实证据自主分析。

`SKILL.md` 的 Markdown 标题与顺序是固定 contract；本文件只示范每段可以多短。

## Ordinary Requirement

用户：“应用列表增加可选排序。”

以下为示例 fixture，不代表当前产品事实：已确认目标是应用列表；后端已有 `name / created_at / id`，支持全结果集分页，当前按 `created_at DESC, id DESC` 排序；尚无排序选择或偏好持久化。真实任务先取得相应证据。

```md
## 现状
应用列表目前按创建时间倒序显示，用户不能切换排序；后端已有名称、创建时间与稳定 ID 字段。
本次需要抉择：提供哪些排序、是否改变默认顺序、是否保存个人偏好。

## 需求分析
目标是让用户按不同查找习惯浏览整个应用列表，翻页仍保持顺序稳定。
建议提供“最新创建、最早创建、名称升序”，保留最新创建为默认；本次不保存跨会话偏好，避免为简单排序增加持久化设置。

## 三个方向（升温发散）
### 保守
- 方案内容：增加“最新创建 / 最早创建”切换，默认最新创建，由后端对完整结果集排序。
- 综合收益：满足时间查找且改动小，但不支持按名称定位。

### 平衡
- 方案内容：增加“最新创建 / 最早创建 / 名称升序”下拉选择，默认最新创建；切换后回到第一页，相同排序值按 ID 稳定排列。
- 综合收益：同时覆盖时间与名称查找，沿用现有字段与分页；关闭页面后回到默认顺序。

### 激进
- 方案内容：在上述三种排序上增加多字段组合，并保存用户的排序偏好。
- 综合收益：适合重复管理大量应用，但需要新增偏好存储和组合排序交互。

## 最终建议（降温收敛）
采用平衡方向：只修改应用列表，提供上述三项，默认“最新创建”，暂不保存个人偏好。
实施时给后端列表接口增加受限排序参数，保留旧请求默认行为；前端增加排序下拉，切换时重置页码。创建时间同值沿用 ID 倒序，名称同值按 ID 升序，保证翻页稳定。
验收检查三种排序、切换后回第一页、同值跨页稳定，以及未传排序参数时仍与当前结果一致。按一个 Single Issue 实施，你确认这套方案即可开始。
```

## Unresolved Decision Boundary

- 若用户只说“这个列表”，且上下文和源码无法确定对象，先指出“缺少目标页面，无法确定接口与可用字段”，请求最小定位信息；不要虚构一个“讨论列表”继续给假具体方案。
- 若对象已知而偏好未指定，应基于当前行为给出默认方案供用户拍板，不把“选哪些字段、什么默认值”重新作为结尾开放题。
- 反例：“建议少量实用排序，确认入口与字段后再固定验收条件。”这没有完成方案收敛，不能作为可执行的最终建议。
- 输出是否合格看用户能否直接决定执行，不只检查标题数量。内部 forward-test 的其他场景、规则路径和调度报告不能拼到用户需求建议里。

## UI Or Flow Requirement

用户：“优化首次进入工作区的引导。”

```text
[进入工作区]
      |
      +-- 已有内容 --> [正常工作区]
      |
      +-- 空工作区 --> [说明] -> [主操作] -> [可见结果]
```

在三个方向中比较引导强度、用户中断成本和状态归属；ASCII 图只表达主路径。

## Diagnostic-Looking Requirement

用户：“为什么新增能配置定时器，编辑却不能，也看不到扩展接口？”

这仍会改变产品入口、contract 与 owner，不是可跳过的事实查询。先取证新增、编辑、后端 DTO 与运行入口，再完整输出 `现状`、`需求分析`、三个方向和 `最终建议`；即使根因已确定，也不以“结论”开头或省略方向。

## High-Risk Contract Requirement

用户：“统一 frontend/backend defaults。”

先读取 `domain-matrix.md`，区分前端展示 fallback、后端默认值、已落库设置和 runtime contract。三个方向都必须说明 source of truth、历史数据影响和验收证据；不要因为名称相同就假设它们是同一概念。

## Plan Shape Selection

普通任务即使同时修改 API、状态和 UI，只要能由一个连贯结果闭环，仍使用 Single Issue。例如“列表支持服务端排序并在当前页面展示”只有一个用户结果，不按 frontend/backend 拆树。

长计划只有在存在多个可独立集成结果时使用 Issue Tree。例如 AI Gateway V3 可以按纵向结果组织：

```text
[Root：V3 可上线并可回滚]
  ├─ [Delivery：Generate 端到端]
  ├─ [Delivery：Compact 与 context transaction]
  └─ [Delivery：双栈 rollout 与 rollback]
```

“先定义类型 → 再写 mapper → 再做 storage → 再补测试”是实现步骤，不是 Delivery Map。
