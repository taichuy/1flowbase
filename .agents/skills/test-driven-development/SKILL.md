# 开发中的验证

先回答：**如果这次改错，用户会看到什么不同？** 预期来自用户目标、协议或领域规则，不从当前代码反推。先定预期，不等于每次先建测试文件。

| 当前任务 | 最短反馈路径 |
| --- | --- |
| 页面调整 / 交互试做 | 先走通目标页面，给用户看效果。已有页面能直接回答的问题，不为预览另建组件快照 |
| 明确缺陷 | 保留真实失败样本、日志或已有失败用例；修后用同一输入对照。适合长期拦截且现有测试抓不到时，再补一个回归 |
| 新规则 / 重构 | 复用所属模块已有用例。新算法用一个不变量或有区分力的边界样本，不按字段、helper 或实现分支逐个建测试 |
| 权限、迁移、事务、持久化 | 动手前固定必须允许和必须拒绝的行为或数据不变量，在真正负责的边界验证；开发可以分步，验收不能略过这些结果 |

同一契约在多个层被调用，不意味着每层都需要相同断言。选择第一次能观察到错误结果的位置；涉及协议映射或真实消费者时，在对应边界验证。

## Execution Cost and Stop Conditions

- Rust 先选 crate / [集成 target](../../../api/apps/api-server/tests/README.md)，再过滤名称；确认目标用例确实执行。API 测试编译成本高不构成顺手改造测试架构的理由。
- 使用仓库资源包装器和 `.1flowbase.verify.local.json`；同 worktree 同时一条 Cargo 命令，多任务共享用户预算。资源失败时换能回答同一问题的轻量入口，或留给 CI，不重复相同构建。[预算与日志细节](references/execution-budget.md)按需读。
- 当前行为已有足够反馈就回到开发或展示；只指出影响本次判断的缺口。正式 QA 集中补相关证据，已执行且相关依赖未变的结果可复用。用户明确要求的发布门禁仍按指定候选执行。
