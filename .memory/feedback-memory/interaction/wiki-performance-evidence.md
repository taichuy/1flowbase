- 规则：报告 Wiki 优化时分别说明当前已部署 Block 的请求次数、真实接口延迟及缓存失效正确性；预览通过不能写成线上已优化，无后端依赖的前端修复不应一并等待重启。
- 原因：用户指出缓存失效无法解释一次点击多次请求及 5–14 秒延迟。实际线上仍是全树查询，主键版只在预览，之前解释未充分区分。
- 适用：低代码 Block 优化与宿主/API 修复并行、后端重启由用户控制的任务。没有复现或阶段计时，不把转发慢直接归为 SQL 慢，也不声称长尾已经解决。

- 后续纠正：用户在了解缓存旧值复现后再次明确要求立即发布 Block，应按最新授权执行，将已知缓存问题独立报告；不能反复以同一问题替用户阻止已要求的发布。必须在实际部署页面验证每次点击请求数，不能以初始化请求减少代替单篇读取验收。
