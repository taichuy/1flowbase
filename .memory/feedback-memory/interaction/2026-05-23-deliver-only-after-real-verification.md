# Deliver Only After Real Verification

## Rule

涉及前端可见效果、接口载荷或用户已经反馈“重启后仍无变化”的修复，交付前必须先拿到可复用证据：目标入口测试、相关组件测试、接口回归或运行态检查至少覆盖用户实际看到的路径。

用户明确给出主页 URL 时，必须从该 URL 开始验收，同时记录最终 URL 和真实内容 ready selector。深链单独可用只能证明目标内容存在，不能证明主入口已接入。

进行中的排障任务里，用户补齐密钥或文件后，应继续原已批准任务；确认补件存在不等于原任务完成。连接故障需要实际验证重连、重试耗尽和协议降级边界，不能只复查凭据后收尾，或把传输错误码直接解释为网络波动。

用户澄清重试归客户端时，先核对网关是否安全、忠实地投影真实错误，再检查目标客户端原会话的实际重试和降级记录。不能仅凭供应商插件未内部重试就宣布缺陷或扩张插件职责；显式把客户端重试设为零的fixture不证明正常预算已耗尽。

网关长会话验收检查真实请求、压缩/subagent控制流程、断连续接与错误终态；模型回忆的逐字精度、推理结论或文案格式不属于网关门禁。模型行为可产生测试负载，但不能把模型质量失败归为网关故障。

## Reason

用户关心的是“重启后打开实际页面是否变化”，不是代码是否看起来改对了。只修局部组件或只跑间接测试，容易漏掉真实入口没有接入、缓存数据仍走旧路径、接口仍一次返回大 JSON 等问题。

正常请求成功不能证明故障后恢复成功；客户端降级与供应商侧降级是不同环节，必须以实际请求、终态和错误记录分别取证。

宿主生命周期故障与真正上游拒绝必须分别归因，避免在错误层级增加恢复掩盖根因；泛化错误不等于完整表达原因，原始对端文本也不能未经安全边界直接透传。

压缩后回忆质量由模型和客户端压缩上下文决定，不能凭字面回答推导网关传输出错；应使用协议事件、原始请求和调用终态验证网关边界。

## Applies When

- 用户反馈实现后重启仍无变化。
- UI 修复涉及多个入口，例如编辑器调试面板和应用日志页。
- 接口改动目标是减少首包体积或延迟加载大字段。
- 最终回复准备声明“完成”“已修复”“可以用了”。

## Practice

最终回复前先说明已覆盖的实际入口和命令结果；若全量构建或全量测试因无关既有问题失败，要明确标注阻塞点，不能把它算作本次通过证据。
