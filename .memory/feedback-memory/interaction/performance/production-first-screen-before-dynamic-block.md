## 规则

用户以项目开发者身份要求生产编译后的打开速度优化时，重点检查源码依赖、实际构建产物和加载关键路径，不以跨境网络、CDN或扩容代替代码方案。真实首屏按1–3秒目标评估，动态代码块（如登录表单）作为第二阶段独立计时；thinking、纯骨架、真实首屏和表单可交互不得混为一个指标。

账号密码内置登录是用户明确要求保留的异常兜底防线。首屏预渲染、依赖拆分或避免重复页面，均不得解释为删除内置登录、将其替换成不可交互静态展示，或强制依赖动态代码块成功。区分“复用源码生成首屏”与“保留可实际认证的内置表单”；认证仍服从既有后端安全策略。本条是方案硬约束，不代表用户已批准某种新入口或切换机制。

## 原因

用户于2026-11-19明确接受动态登录表单二阶段加载，但认为页面本体几十秒才出现不可接受。上一轮侧重公网原因和完整密码框ready时间，未充分回应开发者希望改进生产产物的目标。用户随后澄清：异常情况下必须能使用账号密码登录，不能因优化或去重移除必要的内置登录防线。

## 适用场景

1flowbase公开登录页或同类动态区块页面的编译优化、性能诊断和验收。方案需要实际构建图/体积证据，区别实验结果与目标；保护现有动态能力、会话及后端配置，不用假首屏或删功能凑指标。本反馈不授权直接实现、升级依赖或改线上服务。

2026-11-20 00：用户人工试用新加坡静态首屏候选后明确否决：原 UI 和交互效果不得因性能优化改变。仅把标题和页脚画出来不等于原首屏；同源码抽取的布局也不能证明动画、指针响应、移动断点和原有状态切换等价。此类优化以原页面/交互录屏为基线，分开验证原首屏与动态表单，不允许靠新增过渡状态缩短指标。

2026-11-20 01：用户认可先保原交互的目标，但指出仅说“做异步拆包”不足以执行。此类生产首屏方案需写清具体依赖边、模块归属和触发信号，如何利用现有架构或算法作取舍，以及怎样在真实公网分别证明冷访收益与已有热访体验不退化；不因热缓存掩盖首访成本。

2026-11-20 08：用户指出右侧动态表单等待动画是必要的进度反馈。验收“原交互不变”时，要覆盖真实页面已经出现、内容尚未显示的整个区间；刻意挂起最后一段异步依赖，确认原有反馈确实可见且在动，放行后可输入并撤掉反馈。只检查左侧动画和表单就绪截图会漏掉中间空白。

2026-11-20 09：局部修复后用户人工冷访仍认为与目标有差距时，从最初打开页面开始复核，分别展示“原页面出现前”和“原页面内等待表单”的证据。某段中位数或面板挂载后的逐帧验证不能替代全程；没有用户最新画面时，不替用户认定是哪一段不满意。

2026-11-20 09：用户明确本次不满意的是首次直达时全屏 `thinking` 停留过久，不是表单区的等待提示。处理此类首访问题，先使原动画页面可见、可交互，再在不抢当前交互的前提下异步取得下一步所需的通用依赖；算法建议应指向具体阻塞关系与可验证的结果，而非只报包大小。该优先级不授权绕过会话或部署。

2026-11-20 10：首访截图若只有叶片和 thinking 而缺原页面配置允许的标题、标语与页脚，只能作阻塞诊断，不能作为完成交付。验收从导航开始，分别记录完整可辨认的原画面与真实输入；保留动态表单二阶段，不以假表单填充。

2026-11-20 16：用户提交渲染后表单外观差异和公网登录后工作区报错一起复核；此类对比先核对同入口的实际渲染分支（动态块还是异常兜底），再比较计算样式。登录链须验证跳转后的工作区内容，不把能输入或路由已切换当作工作区可用。
