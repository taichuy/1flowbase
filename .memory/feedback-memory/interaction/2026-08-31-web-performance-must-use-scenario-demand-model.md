# 前端性能优化使用场景需求模型

## 规则

- 不以“每 N 个模块一个包”、仅限制单文件大小或事后增加固定阈值作为完整性能架构。
- 先定义用户交互场景、每个场景所需模块集合、发生概率、缓存状态和时限，再依据模块共现图、网络成本、主线程成本与缓存失效成本形成确定性分区。
- 预算是可观测 SLO 和优化约束，必须由本地与公网真实浏览器轨迹验证和校准，不能替代根因治理。

## 原因

只优化总字节可能产生超大 vendor，只优化单 chunk 大小又可能产生请求爆炸；两者都没有表达“某次交互究竟需要哪些能力”。性能复杂度应由掌握构建图和运行轨迹的 Demand Planner 吸收，而不是泄漏为页面中的零散懒加载判断。

## 2026-11-20 补充边界

- 真实生产静态部署的首包问题，以实际镜像/构建产物、场景依赖闭包和请求时序为证据，不能用开发服务器表现或更换入口版本代替构建优化。
- UI/UX、编辑草稿与既有功能完整性保持；“第二次更快”的 HTTP/模块缓存收益属于必须保留的验收目标。冷启动、暖刷新、同页二次进入及升级后的缓存复用分别验证，不能只优化冷首屏或把等待转移到第一次点击。
- 带宽规格作为已知测量条件，不建议先扩容。区分名义容量、有效吞吐、依赖发现、排队和主线程时间；用字节数除以已经观察到的低吞吐只是在描述结果，不能循环证明根因。

原因：用户针对真实 10 Mbps 部署要求从静态构建架构纠正首包，且明确不允许打断当前 UI/UX 或损失二次访问体验。适用范围为生产前端打包、加载与缓存优化；不把某次线路测量值升级成全局资源假设。

## 2026-11-22 补充边界（容器内普适性与单调过渡体验）

- **严守项目维护者与 Docker 容器内边界**：宿主机内核（如 `sysctl` BBR）、宿主机外层反向代理与用户公网网络环境均属不可控外部条件；一切性能优化方案必须具备产品级开箱即用普适性，改动范围仅限仓库源码与对应 Docker 容器配置，严禁建议修改宿主机环境来掩盖应用层体积、依赖图或调度问题。
- **过渡加载态遵守视觉单调性（禁止多层假动画跳变）**：不得叠加风格/尺寸不一致的临时假壳层骨架或连续多跳路由全屏转圈；每次交互切换在任一视觉区域最多只发生一次从稳态占位到真实内容的收敛，降低用户心智负担。
