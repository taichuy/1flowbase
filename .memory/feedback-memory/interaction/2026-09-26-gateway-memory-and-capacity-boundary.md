# Gateway memory and capacity boundary

## 规则

审计或修改 Gateway Responses 链路时保持协议映射层、AI Native 层、供应商层的职责边界。内存分析分别测量宿主基线、可共享的应用状态、每请求状态和 provider 子进程；不要从总 RSS 推断单请求占用。容量准入依据可观测资源和实际生命周期，不以固定 worker 槽位猜测客户端并发。

指标口径规则：jemalloc `stats.allocated`、`stats.resident`、进程 RSS、进程 PSS 是四种不同口径，不得相互相减，也不得跨进程比较；禁止用「驻留 − 已分配 = 空闲池 + 共享页」这类分解式。删除固定数量门槛（如 64 槽位、128 逻辑会话、4096 binding）属准入语义修正，本身不是降内存措施，需要单独的全局保留预算与释放证据。

准入账本规则：provider worker 的内存预留是按进程最终上限记账的准入账本，不等于已分配物理内存；`MemAvailable` 是瞬时快照而预留是峰值承诺。若休眠 worker 仍保持完整承诺直到确认退出，恢复时无需再次申请同一份承诺；只有承诺已释放，恢复才须重新准入。分析以并发服务能力和内存成本为主，不预设内存波动属于泄漏。

## 原因

用户指出过固定 64 个 worker 槽位会限制服务端并发，并担忧单会话 400–600 MiB 的进程内存波动在高并发、长会话下放大。

## 适用场景

1flowbase AI Gateway 的 Responses 协议实现、provider worker 容量和内存诊断。

## 2026-10-01 process attribution correction

规则：Gateway性能诊断复用项目已有采集，优先核API、插件、测试DB进程CPU秒、RSS/PSS、存储和网络，单列采集器自耗。整机CPU波动通常仅作背景，不据此判定目标进程回归或无谓暂停普通有界取证；重型构建/多agent资源安全与受保护服务不干扰边界仍有效。

原因：用户开发会重启7800；该生命周期中断按时间线归因，不能当网关缺陷，已捕获协议校验错误仍逐条取证。用户允许为验证单独起1flowbase实例及数据库，避免依赖开发服务重启。

适用场景：性能采样、容量诊断和真实模型功能验证；复核原始监听PID/启动时间和私有测试资源，不把背景百分比替代目标服务需求。

## 2026-10-09 protected process boundary

规则：本轮 7600、7800 两端口的现存进程均受保护，仅只读取证，不重启、发送信号、attach 或调用目标函数，不修改产品或插件。开发环境通常可重启的授权不能覆盖本轮观察保护边界，也不能通过批量重启脚本间接操作受保护进程。诊断先以监听 PID、启动时间、实际 executable/cwd 和构建时间定位对象；磁盘工作树 HEAD 不自动代表正在运行的二进制版本。

原因：用户要分析现存进程的内存占用与增长来源，重启会丢失运行历史并干扰该进程；开发目录与 7600 实际运行目录可能不同。

适用场景：当前 7600 内存分析及后续延续排查；用户明确改变边界后按新授权执行。

## 2026-10-09 per-operation cost correction

规则：RSS 回落只证明存在回收，不能证明少量并发下的单位请求或后台任务成本合理。调查需继续量化请求正文、历史事实数量、重复展开、深拷贝与异步持有；分别核对请求执行并发、数据库查询并发和后台投影并发，不以连接数或持久化 waiting 状态代替。优先修复真实成本，不用缩短 allocator decay、缓存 TTL 或猜测性并发上限替代。

原因：用户明确指出少量并发产生大内存仍异常，要求查明放大来源；把可回收等同于正常会漏掉每次操作随历史规模增长的成本。

适用场景：Gateway 内存波动、长会话、日志投影与低并发高成本诊断，以及后续同负载优化验收。

## 2026-10-09 16 resident scope correction

规则：用户明确波动已有其他任务优化且要求「查常驻」时，主线转为长期持有 owner、slab 利用率、分配器元数据和保留生命周期的实际计量；已有波动报告仅作背景，不重复实现或以可回落证明常驻合理。区分实测正文、按分配规格推算的成本与 RSS；没有启动同口径基线和持续生命周期证据时，不宣称完整解释增长或排除慢泄漏。

原因：用户纠正本轮调查范围，只关心现存进程持续维持较高内存的原因，并提供已有波动优化报告避免重复工作。

适用场景：当前 Gateway 常驻内存观察及后续接续诊断；范围随用户最新明确指令更新。

## 2026-10-09 19 baseline comparison correction

规则：用户对照新旧常驻进程追问「多出来的部分」时，优先同窗口比较保留 owner、slab 空槽、tcache 和 base 元数据分类。已经运行数小时的 dev 当前值不能当冷启动基线；「最后事件为 waiting_callback」只是回放库存分类，不能等同启动内存来源或执行并发。源码可解释保留机制，差额归属仍须运行态计量；无法核验的候选 owner 不得推断为空。

原因：单进程的 waiting 数量不足以回答用户要求的额外常驻成本来源，容易把运行历史保留与共同启动成本混为一谈。

适用场景：Gateway / dev 新旧进程内存对照与常驻成本归因。

## 2026-10-09 23 proportional GC design correction

规则：常驻内存治理先复用 storage-ephemeral 的短期热状态与现有数据库事实/归档，不默认扩大成完整事件持久化、同步提交发布门禁或数据库租约容灾系统。短期高频片段与小型定位可缓存，长期上下文仍按数据库引用读取；只有功能所需且无法从既有存储恢复的缺口才补临时分段。缓存到期不等于可删除唯一副本，冷恢复覆盖必须先验证。分别说明内存淘汰、临时数据自动 GC 与业务历史的用户保留策略，使用图示解释触发及删除后行为。

恢复前提规则：按实际读取入口分别核验日志查看、模型续接、checkpoint/callback 恢复与逐事件补读，不把「恢复」默认解释为重播全部长历史。已有归档可回读与 RuntimeEventStream 已接通冷恢复是不同事实；不能以尚未证明的全历史回放需求推动新表、额外归档或将所有会话正文搬入 ephemeral。

最小重建规则：用户要求从已有原始客户端帧、冻结的节点/计划版本、checkpoint 与运行事实推导按需还原路径。按协议输出、业务恢复、历史读模型分别使用已有真值；不能因为某些内部碎片无法逐字反推，就推断业务恢复必须新增全量持久化。原始协议帧不反向取代 Native 状态真值，不以重新执行已完成的模型或工具补历史；没有具体、已确认的功能缺口，不增加持久化系统。

原因：用户指出上一版设计过度强调持久化和容灾，要求发挥 ephemeral 的已有能力，并明确自动回收与用户控制的边界；随后进一步纠正「恢复需要全长历史常驻」这一未经证明的前提，并要求按第一性原理和奥卡姆剃刀优先复用已有存储还原。

适用场景：Gateway 回放缓存、常驻内存、GC 与存储方案设计；不新增未经确认的恢复承诺，不削减既有功能。

## 2026-10-09 23 short-lived callback cache evaluation

规则：数据库按需恢复方案仍应评估快速 callback 的短生命片段复用，不能把「长期上下文不入 ephemeral」误解成禁止近期热数据缓存。分别衡量缓存减少的读取/重建成本与批量写入减少的事务成本；恢复、去重、计费和对外确认所依赖的唯一事实仍按原提交语义处理，可重建或明确允许损失的派生数据才评估异步旁路。TTL、容量配置与具体实现尚未确认。

原因：用户提出快速回调转发通常只需短期输入片段，希望兼顾延迟、数据库负载与常驻内存，而不是把所有读取都留在数据库关键路径，也不希望为此再增加复杂持久化系统。

适用场景：Gateway 近期事件/上下文缓存与同步、异步批量写入方案评估；仍属设计请求，不视为实施授权。
