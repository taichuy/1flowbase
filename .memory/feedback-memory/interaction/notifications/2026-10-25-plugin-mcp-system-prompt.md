- 规则：通讯插件注册专属 MCP 实例和自己的 tools，沿用既有 MCP 渐进式加载体系。插件提供内置系统提示词，用户可编辑；有效提示词以附加系统内容传入 Agent-flow，说明如何查询当前会话的历史消息与用户文件。固定的是使用规则，历史由 AI 按需查询；不默认额外注入近期历史或新建摘要机制。
- 原因：用户明确纠正 Root 将专属 MCP 解释成底座统一历史工具并自动装配近期上下文的方案。用户要 AI 知道查询入口，主动翻历史获取所需上下文。
- 适用：通讯中心、微信等通讯插件的 MCP 注册、提示词编辑与 Agent-flow 运行装配；此纠正不表示授权放宽后端数据隔离，也不等同整个跨仓执行计划已经批准。

- 消息装配补充（2026-10-25 11）：用户要求每轮三条独立消息，顺序为稳定系统提示词、底座生成的会话信息、当前用户消息。会话信息从固定提示词中分离，保持同会话前缀稳定以利于供应商提示词缓存；不得承诺跨身份或任意供应商必然命中。创建渠道时默认加入插件注册的专属 MCP 实例，同时沿用 AI 助手的多个 MCP 实例选择能力。

- 2026-11-13 用户进一步明确：文件同样采用按需工具路线。AI 从聊天记录获取文件元信息，通过已选择 MCP 查文件/看图；底座不直接注入图片字节。用户要求文件处理时，可发现已授权的 `/terminal/terminal_info` 和终端文件工具下载处理，MCP 选择本身表达工作权限，不由微信插件隐式添加终端授权。
- 2026-11-13 用户明确内置实例 ID/名称为 `wechat-chat-channels`；由插件提供，缺失则新增、存在则强制更新完整定义，旧插件工具不保留，随插件升级。此规则覆盖旧“每渠道生成一个 MCP、已有跳过”的阶段实现；渠道/工作区/发送者隔离仍由 Host 固定，用户添加的其他 MCP 不受覆盖。原因：用户发现微信 MCP 名称混乱、旧工具不会更新，且模型拿到文件ID后无法看图。适用：微信插件内置 MCP 的声明、激活、更新和文件调用链。
