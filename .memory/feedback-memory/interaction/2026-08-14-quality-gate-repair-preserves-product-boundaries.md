# 质量门禁修复的产品边界与资源预算

## 规则

- 禁止为通过门禁改动既有用户可见的 UI 文案、样式或布局；先保持功能可用性与状态机不变量，再考虑性能或工程优化。
- 基础镜像与依赖扫描出的安全漏洞在用户未纳入处理范围时只作为 warning，不触发升级。
- 旧门禁、旧断言或重复门禁没有当前价值时应删除或更新，不能让它们持续阻塞开发。
- 少于三个失败门禁反复失败时，先取得定向本地证据，再在线上跑相应窄范围，最后运行一次最终全量门禁；全量运行应控制在一小时内。

## 原因

质量门禁用于保护产品行为和交付效率，不得诱导以修改 UI、削弱状态转换或无关基础依赖升级换取绿灯。

## 适用场景

- beta / CI 门禁修复与在线值守。
- React Doctor、后端测试分片、覆盖率、协议一致性和容器扫描等组合门禁。

## 完整第一方治理范围（2026-10-19纠正）

- 规则：用户要求完整质量治理时，不得擅自缩小为少数 lint/runtime 类别，把 act、结构规模、React Doctor 或未审计第一方 warning 以“既有债”排除；旧 CI 绿灯不证明剩余项合法。逐项整改真实问题，合法动态资源/协议兼容须给出当前生产者、消费者、测试与迁移证据。所有门禁先线上，持续失败剩余≤3才可本地。
- 原因：用户明确否定交付中仍保留这些问题的做法。门禁必须保护当前代码约束、功能完整性和维护性；仅解释或缩小验收范围不能完成授权。
- 适用：全量质量门禁修复、warning 清理、项目健康验收；上游包/容器漏洞仍单独归因，不借此跳过第一方调用。
