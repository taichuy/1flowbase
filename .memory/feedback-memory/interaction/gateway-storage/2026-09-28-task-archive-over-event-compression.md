规则：用户明确拒绝把所有逐片事件长期保留、仅改压缩/共享表示当成最终日志方案。重新设计必须先区分实时变化通知、真实item/节点/调用事实、恢复/投递状态与长期详情；可归并delta不逐次创建永久事件或Message/Reasoning对象。用户随后细化为一个任务保存拓扑/执行路径，各真实节点执行实例分别保存详情，优先复用既有元数据与按节点读接口；不再坚持整任务一份大正文或全任务固定几行。客户端请求可能跨节点，原始轨迹保持独立采集归属，节点只定位其真实关联。

原因：事件关系行、JSON封装和索引成本可能超过片段正文；节点分存符合UI访问粒度，控制并发归档/读取时的内存与任务级写入竞争，已完成节点不必等待整任务结束。此前47.3%/57.1%实验只验证了旧全事件表示的收益，未解决持久化语义和生命周期问题，不能当作新节点归档设计的量化；节点拆分本身也不能冒充压缩率收益。

适用场景：本次Gateway日志详情/运行态方案及后续实施。继续保留发布工作流/API、客户端真实raw/分片/方向/时间、节点执行顺序与三层职责；任务统计/对话保持纯文本记录。ephemeral仅承载可重建短期热数据，长期上下文按DB locator查询；恢复、未ACK状态、已确认采集不能只留cache或等任务结束首次落库。日志关系行可随真实节点及物理正文部分增长，但不能随每个内部delta增长；节点attempt、resume按原执行身份，不为日志优化扩张业务执行能力。统一设计继续在tmp/gateway-storage-review/优化方案.md维护。
