## 规则

- 讨论进程池、SDK 或事件循环前，先闭合用户实际症状、已确认代码事实、尚未验证的因果与成功标准。用户要求回到问题时先暂停方案扩展；不能把理论内存准入推算当成现场故障已复现，也不能把技术手段当成交付目标。
- 用户已明确本轮问题是插件执行粒度与固定资源限制带来的额外开销和容量利用不足风险；用户实际观察是每开会话新增子进程，尚未提供资源限制导致请求失败的运行证据。资源效率与容量伸缩本身足以作为目标，不反复要求先给出断流或报错才能推进问题定义。
- 设计共用插件运行机制时，不默认把新增业务插件或迁移无关插件作为通用性验收的前提；先说明现有测试与最小夹具能覆盖什么，真实跨插件接入仍未验证什么。
- 不把“真实模型验证仅有 Luna”解释成“其他现有供应商无需分析或适配”。用户指出 Anthropic、Gemini、DeepSeek 等每调用启动进程的插件也可能存在同类资源问题；应区分实际受影响的现有插件与为验证而新增的无关插件。本轮用户明确排除 `chatgpt-codex` 插件，仍可参考独立的本地 Codex 官方源码。
- 解释方案时明确 Host 是现有 `runtime-extension-host` 宿主模块；区分复用现有运行 owner、插件侧 SDK 与新增插件/服务，避免让用户误以为要额外建设一套 Host。
- 清楚区分测试代码、需要安装发布的业务插件、真实模型 API 请求；不能把前者包装成后两者的验收证据。
- 性能及资源改动要给出同条件的旧版/新版比较：实际在途调用、进程数、实际内存、准入等待及完成结果，而非仅承诺并发数字。
- 本任务直接在 `/home/taichuy/git/1flowbase_gateway` 的 `gateway` 分支开发；该工作树已由用户专门创建，不再创建额外工作树或 assembly 分支。跨仓插件改动留在官方插件仓，Root 独占提交与集成。

## 原因

用户已对 1flowbase 底座投入大量内存优化，希望可用资源能转化为有效请求处理能力，避免插件进程开销或固定容量提前成为瓶颈。优先级为功能完整性 > 可靠性 > 性能 > 可演进性；不为证明未来能力扩大产品开发与验证成本。本次用户只提供 gpt-6-luna、推理强度 max 用于真实验证。

## 适用场景

插件运行层重构、并发与资源管理设计、决定是否新增插件或扩大真实模型验证矩阵。
