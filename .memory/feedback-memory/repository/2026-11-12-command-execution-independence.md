- 规则：每条聊天事件指令一对一执行。出错结束该次指令并保留错误，不能让旧错误持续阻塞后续指令；只有同一对话仍在生成回复时，追加指令才排队。
- 原因：用户纠正将旧指令未结束造成的阻塞说成正常排队。指令之间没有业务依赖，错误不能传播到后续指令或把多条指令合并成一次执行。
- 适用场景：聊天自定义事件指令及报告工作流的状态、调度设计与验收。既有接收顺序/worker 串行实现不能冒充该规则已经完整实现或验证；内置 /new 的中断语义另行保留。
- 2026-11-12 用户进一步明确：指令/事件各自独立，对话是线性的，前一答案生成期间可继续追加输入；AI 应通过独立保存的会话历史看到本会话内的指令和事件回复。独立事件身份不自动等于并发执行；不能把全部事件硬并入某一个普通 AI 回复轮次，也不能把发送日志存在当作 AI 历史已可见。核对历史时必须检查最终模型使用的 history_messages 数据源是否覆盖事件回复。
- 用户随后纠正：发送消息历史应覆盖对应插件通道，底座与插件协议需要一起完善；不能把缺失归档只作为排盘工作流的专用补丁。适用于通道发送、标准回执与AI历史的联动设计。具体协议方案仍需依据当前契约收敛；此纠正不等于插件应直接拥有底座业务数据库或可自行扩大会话权限。
- 最新明确纠正：八字与紫微应是两条不同指令、两个独立事件、两次独立工作流，各返回一份对应报告。此前把“紫微也加进去”做成同一 /paipan 执行中发送八字和紫微两份报告，是 Agent 对需求的错误理解，不能作为用户确认过的设计继续沿用；也不能用此错误实现推导本需求必须扩展为一条输入对应多条报告。用户随后授权开始修复；本轮以 /paipan（八字）和 /ziwei（紫微）落地，不能再沿用同一命令双报告的旧配置。
