## 规则
用户于2026-11-01纠正：组件数据首先核对插件注册规范；代码模板列表不可滚动等通用交互属于底座职责。
不要用“两个系统各自投影”合理化同一组件的重复注册，也不要让插件承接底座列表的布局修复。
用户同日再次纠正组件编码：自动注册应先对齐既有组件规范，不得自行把内部哈希设计成面向用户的业务编码。诊断须区分已执行的校验规则与既有命名惯例；不能用“能通过校验”合理化另创编码体系，也不能只改前端显示别名。

## 原因
底座负责统一交互和执行声明；插件负责准确声明其能力归属。展示入口不能替代清晰注册契约。

## 适用场景
插件能力在代码模板和组件管理重复出现、注册自动化，以及底座通用列表交互修复。

## 组合式组件与模板边界（2026-11-01）
- 规则：用户认可复用既有历法/排盘依赖，但纠正只在区块中挂载整页黑盒的交付方式。插件应提供可组合组件与必要的共享状态能力；完整页面组合源码归模板，用户能继续导入已授权依赖、修改布局和逻辑。
- 原因：独立导出却无法共享状态不等于可组合；包被打进插件内部也不等于用户源码可以导入。避免以整页封装剥夺低代码编辑能力。
- 适用场景：插件迁移整页、UI组件注册、页面模板设计与低代码依赖开放。用户随后明确批准开始调整。实现仍复用底座现有模块授权与模板机制，不新建注册体系；实际可用性必须以版本化插件与可编辑页面的运行证据结算。

## 日历组合的滚动边界（2026-11-01）
- 规则：桌面组合左右分栏，左侧黄历、出生信息与排盘内容滚动时，右侧日历应保持可见；矮窗口允许日历独立滚动，手机端单列。布局继续属于可编辑组合源码及对应页面模板，不退回整页黑盒。
- 原因：用户需要查看左侧八字/紫微时持续使用日历，而不是让短日历跟随长内容一起消失。
- 适用场景：日历组合模板、相同的兼容整页布局；不把此局部布局需求变成底座全局滚动覆写。

## 日历组合的区块内比例（2026-11-01）
- 规则：用户要求区块范围内按「左留白 : 详情 : 间隔 : 日历 = 0.3 : 6 : 0.3 : 3.4」布局，优先复用 Ant Design 布局组件。以区块自身宽度响应，而不是用浏览器宽度推断区块大小；窄区块保证日历可用，手机单列。
- 原因：用户反馈原 1 : 6 : 1 : 2 两处留白过大、日历偏窄；两处留白各缩到 0.3，省下宽度全部分配到日历，详情保持 6。 用户随后明确认可当前效果；后续接口化评估不应顺带调整已确认布局。
- 适用场景：本次可编辑组合页、其组合模板以及兼容整页布局；保留此前日历 sticky 和独立滚动边界。
