## 规则

资源预算按用户明确授权调整，不仅因 CPU 空闲或编译耗时就继续扩大。

2026-10-18 用户在体验串行和分阶段预热后，明确允许单个阶段使用一半 CPU：预热独立采用一半可用逻辑 CPU 的 Cargo 并发预算，先获取锁定依赖，再按顺序完成普通库和全量测试预编译，避免前后阶段竞争。

2026-10-19 用户进一步明确授权把日常开发测试也开放到一半可用 CPU；共享 `cargoJobs` / `cargoTestThreads` 与系统 Cargo 包装器可据此调整，不再沿用此前固定为 2 的限制。保留多 worktree 的任务并发语义、预热阶段顺序及内存保护。

同日用户纠正：项目是开源开发环境，需要适配其他开发者的机器；半机 CPU 必须按运行环境自动计算，不能把当前 20 CPU 得到的 10 写成通用固定值。显式本地覆盖仍属于开发者自己的选择。

随后用户明确：2 核、8 GiB 指 Rust 构建预算下限，不是整机最低配置；低配机器允许超过半机。资源充足时 CPU 和内存通常取一半，不能把这条规则解释成任何机器都严格限于一半。实际容量不足时仍受容量和系统内存余量约束，最低硬件是否能完成冷构建须另行验证。

源码开发环境仍需完整预热测试；先完成启动目标编译，再串行预热测试，不把取消测试预热作为优化结果。

## 原因

资源配置已有用户调优依据；缺少预热会让后续 AI 开发时的测试构建成本难以控制。

用户设置两个任务时考虑了多个 worktree 同时工作的资源需求，同时希望避免单核等待；需区分跨 worktree 构建任务和单次 Cargo 的内部并行预算，不把 CPU 空闲直接解释为资源限制失效，也不只为提升 CPU 占用而恢复大型目标同时编译。

## 适用场景

Rust 冷构建、缓存清理、预热脚本与 AI 开发验证成本优化。

## 用户终止重型验证后的处理

- 规则：用户因资源消耗手动终止本地大型宿主编译后，该任务不原样重跑、不提高本地资源预算；将后续重型构建和回归移到 GitHub Actions，下载候选产物在本地做必要的运行验证。
- 原因：2026-10-24 弱网修复的 api-server lib-test 编译运行约 551 秒后被用户主动终止。SIGTERM 应归因为用户取消，不能猜为 OOM，也不能将零用例视作测试失败或通过。
- 适用场景：资源消耗已影响用户正常工作的 Rust 宿主验证；历史预热预算数字以 `.memory/user-memory.md` 的最新偏好为准，不借此修改通用预算配置。

## 半机配额与整机卡顿的边界

- 规则：用户反馈 Rust 测试导致系统卡顿时，核对实际限制和故障时段的整机资源证据；不能仅凭并发为半数或 MemoryMax 为半机就断言不会影响桌面。定向测试的准入需考虑实际编译目标成本，沿用重型后端门禁默认 CI 的偏好，不擅自扩大成全系统实时调度。
- 原因：2026-10-24 用户再次指出半机限制下仍接近宕机；历史采样证实该次 rustc 常驻内存约占整机 31% 时，整机已出现持续内存回收阻塞和高内核 CPU，取消编译后压力恢复。Rust 组额度不能代表整机仍有足够余量。
- 适用场景：大型 Rust 宿主测试、重门禁资源事故诊断及本地/CI 执行位置选择。
